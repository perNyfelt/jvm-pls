# Phase 6 Implementation Plan

## Goal

Implement Phase 6 from [`req/v1.0.0-roadmap.md`](/home/per/project/jvm-pls/req/v1.0.0-roadmap.md): Tier 1 and Tier 2 LSP features on top of the Phase 1-5 core, type, build, and Groovy-dynamic foundations.

The target outcome is that the server is no longer just a completion/definition engine. It should provide the first complete editor workflow:

- hover with type/signature/documentation for source and binary symbols
- semantic diagnostics beyond parse errors
- references, document symbols, and workspace symbol search
- signature help driven by the Phase 4 overload model
- code actions for import and basic stub workflows

This phase should also connect the constructor-capable model added in Phase 5 into classpath and JDK symbols for hover, signature help, and future constructor-aware code actions.

## Scope

Phase 6 should cover:

- `textDocument/hover`
- semantic diagnostics beyond parse/compiler errors
- `textDocument/references`
- `textDocument/documentSymbol`
- `workspace/symbol`
- `textDocument/signatureHelp`
- `textDocument/codeAction`
- reverse reference tracking in core
- constructor support for classpath/JDK symbols in presentation/query paths
- LSP wiring in `jvmpls-server` for all of the above

Phase 6 should not try to finish:

- rename or workspace edits beyond narrow code actions
- formatting
- implementation/typeDefinition/call hierarchy
- full incremental dependency-aware reanalysis from Phase 8
- deep framework-specific documentation providers

Known Phase 6 limitation:

- reference tracking can be workspace-global rather than per-module-precise at first, matching the existing Phase 3 workspace-wide classpath limitation

## Architectural Direction

Phase 6 should extend the current architecture rather than layering ad hoc feature-specific side paths on top of it.

That means:

- `jvmpls-core` should own the reusable query/index pieces for references, symbols, signature candidates, and hover payloads
- `jvmpls-server` should stay as the transport and LSP-shape adapter
- Java and Groovy plugins should report richer symbol, reference, and diagnostic data during normal indexing instead of building separate per-feature indexes
- source and external symbols should flow through the same constructor-capable type/signature model introduced in Phases 4-5

Three design rules should be explicit:

- hover, signature help, and code actions should consume the same underlying symbol/type data rather than rebuilding partial analyses
- diagnostics should share the same member/type resolution helpers already used by completion and definition wherever possible
- references should be reported during indexing, not discovered later by rescanning source on demand

## Core Design Decisions

### 1. Hover needs a real transport-neutral payload

Do not make hover a server-only string formatter.

Recommended shape:

- add a transport-neutral `HoverInfo` model in `jvmpls-core`
- include:
  - display title or symbol label
  - resolved type / method or constructor signature
  - documentation text when available
  - provenance/inference hints for synthetic or dynamic symbols
  - declaration location when useful for fallback presentation

`jvmpls-server` should only map `HoverInfo` to LSP `Hover`.

### 2. References should be a first-class index feature

Do not bolt references onto LSP handlers by reparsing the workspace.

Recommended additions:

- a reverse reference map in `SymbolIndex`
- `SymbolReporter.reportReference(String targetFqn, Location useSite)`
- per-file ownership of reference entries so reindex/remove can replace them cleanly

This should be additive to existing symbol indexing, not a separate store hidden in the plugins.

### 3. Diagnostics should be layered, not monolithic

Phase 6 diagnostics should be split into:

- language parse/compiler diagnostics from the existing plugin flows
- core/shared semantic checks that apply when enough symbol/type information exists
- Groovy-specific dynamic relaxations that downgrade or suppress false positives in dynamic contexts

This avoids turning one plugin class into an even larger catch-all semantic engine.

### 4. Signature help and constructor UX should share one callable model

Phase 6 is the point where constructor-capable symbols need to be fully connected for external types.

Recommended rule:

- methods and constructors should both surface through one callable-candidate path
- signature help should not care whether the active callable comes from source, classpath, or JDK symbols
- hover and code actions should reuse the same callable rendering utilities

### 5. Code actions should be diagnostics-driven when possible

The first code actions should attach to known diagnostics and existing import/stub data rather than trying to invent broad refactoring infrastructure.

Recommended first set:

- auto-import for unresolved type names
- organize imports for unused/duplicate imports
- add missing method stub for abstract/interface inheritance cases already visible in the type model

## Workstreams

### 1. Add core hover and callable presentation models

Add transport-neutral core models for:

- `HoverInfo`
- `CallableInfo` or equivalent reusable method/constructor presentation shape
- optional lightweight `DocumentationInfo` abstraction if needed to distinguish plain text vs markdown

These models should be able to represent:

- fields
- methods
- constructors
- synthetic/dynamic provenance
- external symbols with no docs attached

### 2. Extend classpath/JDK symbol materialization to include constructors

Phase 5 intentionally stopped short of binary constructor support. Phase 6 should finish that handoff in `jvmpls-classpath`.

Required work:

- have `BinaryTypeReader` capture constructor members with the constructor-capable model
- have `ClasspathSymbolProvider` materialize constructors for external classes
- expose those constructors through the same query path used by source constructors
- ensure JDK classes participate too

This is a prerequisite for useful hover/signature help on `new Foo(...)` for external types.

### 3. Add hover query support in core

Add a new core query/API surface for hover resolution.

Recommended shape:

- `Optional<HoverInfo> hover(String fileUri, Position position)`

Implementation should:

- identify the symbol/callable/expression under the cursor
- reuse existing definition and typed-resolution paths where possible
- include synthetic provenance text for Phase 5 dynamic members
- fall back gracefully when documentation is unavailable

This should not be implemented as a server-only wrapper around definition.

### 4. Add documentation extraction pipeline

Phase 6 hover needs docs, not just types.

Recommended sources:

- Java source Javadoc from AST/source text
- Groovy source Groovydoc or leading doc comments where available
- binary symbols from attached source or Javadoc artifacts when available
- otherwise signature/type-only hover

Recommended implementation order:

1. source comments first
2. binary signature-only fallback
3. attached binary docs as optional enhancement inside the same workstream

Do not block hover shipping on full remote Javadoc artifact resolution.

### 5. Add reverse reference indexing in core

Extend `SymbolIndex` and `SymbolReporter` so plugins can report references during indexing.

Required behavior:

- per-symbol reverse map from target FQN to use sites
- per-file reference ownership so `removeFile()`/reindex can replace stale entries
- support for methods, fields, constructors, and types
- no duplicate use sites from one file/index pass

### 6. Update Java and Groovy plugins to report references

Both plugins already walk the AST. Phase 6 should add reference reporting during that walk.

Recommended targets:

- type references
- field/property references
- method call references
- constructor call references
- extends/implements references
- import references when useful for workspace symbol/ref tooling

Groovy should reuse the Phase 5 shared member resolver so dynamic/synthetic member references land on the same symbols used by completion/definition.

### 7. Add `textDocument/references`

Once reverse indexing exists, add a core query plus LSP wiring for references.

Recommended behavior:

- definition symbol under cursor resolves to a stable symbol key
- reverse index returns all known use sites
- include declaration optionally when the client requests it
- work cross-language where Java and Groovy resolve to the same symbol FQNs

### 8. Add document symbols and workspace symbol search

These are lower-risk and should build on existing indexed data.

For `documentSymbol`:

- expose the file’s declared classes, methods, fields, constructors, and major synthetic members where helpful
- keep it source-oriented; do not inject unrelated workspace symbols

For `workspace/symbol`:

- add fuzzy or prefix/substring search over the indexed symbol set
- include external symbols where useful, but rank source/workspace results ahead of binary symbols
- filter noisy synthetic members unless they are directly useful to users

### 9. Add semantic diagnostics in layers

Implement the non-parse diagnostics from the roadmap using shared resolution helpers.

Recommended initial set:

- unresolved symbols
- type mismatches for assignments and arguments when types are known
- unused imports
- duplicate declarations
- access modifier violations
- missing/excess method arguments

Recommended sequencing:

1. unused imports and duplicate declarations
2. unresolved symbols and access checks
3. missing/excess argument checks
4. type mismatch checks

Groovy dynamic relaxations should continue to downgrade or suppress false positives in dynamic contexts rather than duplicating the Phase 5 logic.

### 10. Add signature help

Add a callable-resolution path for an active call site and map it to LSP `SignatureHelp`.

Required behavior:

- identify the active argument index inside `(...)`
- collect method and constructor overload candidates
- rank using the Phase 4 typed overload logic
- show parameter names, parameter types, return type, and docs when available
- support both method calls and constructor calls

This should be implemented after constructor-capable external symbols are wired in.

### 11. Add code actions

Start with narrow, deterministic actions.

Recommended first actions:

- auto-import unresolved type
- organize imports
- add missing method stub when a class extends/implements a type that requires it

Recommended design:

- diagnostics produce stable codes and enough context to attach fixes
- plugin/core provides `TextEdit` or workspace-edit candidates
- server maps them to LSP `CodeAction`

Avoid Phase 6 scope creep into rename-like multi-file transformations.

### 12. Refactor shared rendering/resolution utilities

By this point several features will need the same formatting and lookup logic.

Extract shared utilities for:

- rendering typed method/constructor signatures
- symbol-to-hover presentation
- symbol-to-signature-help presentation
- symbol matching/ranking for workspace symbol search
- import/code-action eligibility checks

This workstream is important to prevent `JvmPlsTextDocumentService` and the plugins from gaining duplicated feature logic.

## Recommended Sequence

1. core hover/callable presentation model
2. classpath/JDK constructor materialization
3. core hover query support
4. reverse reference indexing in core
5. Java/Groovy reference reporting
6. `textDocument/references`
7. `documentSymbol` and `workspace/symbol`
8. semantic diagnostics layer
9. signature help
10. code actions
11. shared rendering/refactor cleanup

## Tests

Phase 6 needs direct coverage in three layers.

Core/unit coverage:

- hover payload rendering for fields, methods, constructors, and synthetic members
- reverse reference map add/remove/reindex behavior
- workspace symbol matching/ranking
- signature-help candidate selection and active-parameter detection
- diagnostics helpers for unresolved symbol, arity, and access checks

Classpath coverage:

- external constructor materialization from JDK and JAR symbols
- hover/signature rendering for external constructors and methods

Plugin coverage:

- Java and Groovy reference reporting for types, members, and constructors
- Groovy hover/diagnostic behavior for synthetic Phase 5 members
- cross-language references where Java calls Groovy symbols and vice versa

Server/integration coverage:

- `textDocument/hover` for source and external symbols
- `textDocument/references` cross-language
- `textDocument/documentSymbol`
- `workspace/symbol`
- `textDocument/signatureHelp` for methods and constructors
- `textDocument/codeAction` for auto-import and organize imports
- semantic diagnostics published with stable codes and sensible severities

## Main Risks

- letting hover, signature help, and code actions each build their own partial callable model
- bolting references onto the server instead of indexing them in core
- widening Groovy semantic diagnostics without respecting Phase 5 dynamic relaxations
- overloading workspace symbol search with noisy synthetic/external results
- delaying external constructor support until after signature help, which would split source and binary behavior again

## Success Criteria

Phase 6 is done when:

- hovering over a source or external symbol shows type/signature information and docs when available
- semantic diagnostics catch the roadmap’s core error categories without regressing dynamic Groovy behavior
- references work across Java and Groovy for shared symbols
- document/workspace symbol queries are useful in real projects
- signature help works for methods and constructors from both source and binary symbols
- code actions provide at least auto-import and organize-import support through LSP
