# Phase 8 Implementation Plan

## Goal

Implement Phase 8 from [req/v1.0.0-roadmap.md](/home/per/project/jvm-pls/req/v1.0.0-roadmap.md): incremental analysis, caching, and performance work on top of the Phase 1-7 server, indexing, classpath, and LSP features.

The target outcome is that `jvm-pls` stops treating every edit as a near-full reanalysis event and instead behaves like a long-lived workspace service:

- file changes reindex only the files that actually need it
- document changes can be applied incrementally
- warm restart avoids rescanning everything from scratch
- indexing and classpath work stay responsive under load
- long-running requests can be canceled

Phase 8 should improve latency and scale without changing the core symbol model or feature semantics established in earlier phases.

## Scope

Phase 8 should cover:

- activation of `DependencyGraph` for file-level invalidation
- dirty-file propagation with direct and conditional transitive reindexing
- incremental text sync at the LSP/server and core document-store layers
- AST caching in Java and Groovy plugins
- persistent classpath symbol cache under `.jvmpls/`
- persistent symbol-index snapshot support for warm restart
- broader use of the existing virtual-thread executor for background indexing and cache I/O
- honoring LSP `$/cancelRequest`
- a benchmark/performance test slice with synthetic workspaces

Phase 8 should not try to finish:

- semantic changes to completions, definitions, rename, or call hierarchy beyond performance improvements
- advanced distributed cache formats or cross-machine cache portability
- speculative background indexing of unopened files beyond dependency-driven work
- fine-grained AST patching deeper than method-body reuse
- range-level incremental reparsing if file-level reindexing plus AST reuse is already fast enough

## Current State

The current codebase already has the right anchors for this phase, but most are still minimal:

- [`DependencyGraph.java`](/home/per/project/jvm-pls/jvmpls-core/src/main/java/se/alipsa/jvmpls/core/DependencyGraph.java) stores only lightweight forward edges and is not yet used to drive invalidation
- [`DocumentStore.java`](/home/per/project/jvm-pls/jvmpls-core/src/main/java/se/alipsa/jvmpls/core/DocumentStore.java) only supports full text replacement
- [`JvmPlsTextDocumentService.java`](/home/per/project/jvm-pls/jvmpls-server/src/main/java/se/alipsa/jvmpls/server/JvmPlsTextDocumentService.java) still advertises `TextDocumentSyncKind.Full` and handles `didChange` as full sync
- [`CoreEngine.java`](/home/per/project/jvm-pls/jvmpls-core/src/main/java/se/alipsa/jvmpls/core/CoreEngine.java) reindexes the changed file directly and does not propagate dependency invalidation
- `JavaPlugin` and `GroovyPlugin` keep some per-file parse context, but not a deliberate structural AST cache keyed for incremental reuse
- [`BinaryTypeReader.java`](/home/per/project/jvm-pls/jvmpls-classpath/src/main/java/se/alipsa/jvmpls/classpath/BinaryTypeReader.java) caches in memory only
- `CoreServer` already creates a virtual-thread executor, but indexing, cache persistence, and request cancellation are not consistently modeled around it

Phase 8 should build on these existing pieces rather than replacing them.

## Architectural Direction

Phase 8 should introduce three durable capabilities:

1. `Incremental workspace state`
   - source text, file dependencies, and API fingerprints must be first-class tracked state
   - change handling should decide what to reindex based on dependency and signature impact, not just on “file changed”

2. `Persistent warm-start data`
   - classpath metadata and symbol-index snapshots should survive process restart in `.jvmpls/`
   - cache loading must be validated against timestamps, versions, and workspace shape before reuse

3. `Cancelable background work`
   - indexing and cache work should run through the existing executor
   - request handlers and background jobs should check cancellation and stop cleanly when the client no longer cares

The important rule for this phase is that correctness wins over aggressiveness. If cache validation or incremental reuse is uncertain, the implementation should fall back to full parse or full reindex.

## Core Design Decisions

### 1. Dependency tracking needs both forward and reverse views

`DependencyGraph` should stop being a passive forward-edge bag.

Recommended evolution:

- store normalized file-to-file dependency edges
- optionally retain referenced symbol/API keys when useful for signature invalidation
- maintain reverse dependents for cheap “who needs reindexing?” queries
- support per-file dependency replacement on reindex

Recommended API additions:

- `replaceDependencies(String fromUri, Collection<String> toUris)`
- `directDependentsOf(String uri)`
- `transitiveDependentsOf(String uri)`
- optional support for per-file exported API fingerprints

This keeps invalidation decisions in core instead of scattering them through plugins or the LSP layer.

### 2. Dirty propagation should distinguish implementation changes from API changes

The roadmap requirement is:

- direct dependents on any file change
- transitive propagation only when a public API signature changes

Recommended implementation:

- compute a stable per-file `ApiFingerprint` from exported declarations
- compare the new fingerprint with the previous one during reindex
- if unchanged: reindex the changed file plus direct dependents only
- if changed: walk the transitive reverse dependency graph

This gives predictable behavior without attempting fully semantic impact analysis.

### 3. Incremental sync should be applied to source state before semantic work

Do not push LSP incremental edit semantics down into the plugins directly.

Recommended shape:

- `JvmPlsLanguageServer` advertises `TextDocumentSyncKind.Incremental`
- `JvmPlsTextDocumentService.didChange(...)` applies ranged edits to `OpenDocuments`
- `CoreFacade.changeFile(...)` still receives the resulting full text for now
- `DocumentStore` grows an edit-application helper so core-owned text can stay consistent with server-owned text

This preserves the plugin contract while removing the cost of full-content replacement over the transport.

### 4. AST caching should be structure-aware, not token-diff clever

Phase 8 should not attempt fine-grained AST surgery.

Recommended first version:

- cache the last parsed top-level structure per file
- detect whether imports, package, class header, member signatures, or member list changed
- if only method or script bodies changed, reuse the previous structure-derived symbol/dependency metadata where safe
- otherwise fall back to a full reparse and rebuild

The value here is predictable reuse, not maximal sophistication.

### 5. Persistent caches should be versioned and disposable

Both classpath cache and symbol snapshots should be treated as optional accelerators.

Recommended cache rules:

- store under `.jvmpls/` in the workspace root
- include tool version and schema version in every cache artifact
- validate against JAR timestamps, workspace roots, and relevant settings
- delete or ignore unreadable/stale cache data rather than trying to heal it in place

This avoids turning performance work into a source of persistent corruption.

### 6. Cancellation should be explicit in request execution

LSP request handlers currently rely on `CompletableFuture.supplyAsync(...)` without shared cancellation state.

Recommended additions:

- a `CancellationRegistry` in `jvmpls-server` keyed by request id
- request-scoped cancellation tokens visible to long-running server/core operations
- explicit checks before expensive index/classpath work and between major steps
- cancellation-safe cleanup for background tasks

If full request-id plumbing is awkward in the first pass, Phase 8 should at minimum support cooperative cancellation for the heaviest request families and background indexing.

## Workstreams

### 1. Upgrade dependency reporting and graph queries

Required work:

- extend `SymbolReporter` or a sibling reporting surface so plugins can report file dependencies during `index()`
- update `JavaPlugin` to report imports, resolved type references, extends/implements, and other file-level dependencies
- update `GroovyPlugin` to report imports, explicit type references, script/class relationships, and best-effort dynamic dependencies
- replace `DependencyGraph`’s current forward-only storage with per-file replacement plus reverse lookups

Expected output:

- changed files can ask core for direct and transitive dependents without scanning the entire workspace

### 2. Add file API fingerprints and invalidation policy in core

Required work:

- introduce an `ApiFingerprint` model or equivalent stable digest
- compute exported API shape from declarations already in `SymbolIndex`
- persist prior fingerprints per file
- teach `CoreEngine.openFile(...)`, `changeFile(...)`, `analyze(...)`, and watched-file handling to:
  1. reindex the changed file
  2. compare old/new API fingerprint
  3. schedule direct or transitive dependents accordingly

`ApiFingerprint` should be structural rather than textual. It should include:

- exported type names and their kinds such as class, interface, enum, annotation, or record if/when supported
- public and protected method signatures:
  - method name
  - parameter types in declaration order
  - return type
- public and protected field names and declared types
- supertype relationships such as extends and implements
- relevant modifier changes such as `public`, `protected`, `static`, `final`, `abstract`

`ApiFingerprint` should explicitly exclude:

- method and constructor bodies
- private members
- comments and formatting
- local variables and local control-flow changes

Recommended representation:

- a normalized structural digest built from sorted declaration records, then hashed
- avoid raw source-text hashing because it would treat formatting and comment changes as API changes

Recommended implementation note:

- keep reindex scheduling deterministic and deduplicated with a queue/set per change event

### 3. Implement incremental document sync

Required work:

- change server capabilities from full sync to incremental sync
- add range-based edit application to `OpenDocuments`
- add matching range-based text application helper in `DocumentStore` or shared utility code
- update `JvmPlsTextDocumentService.didChange(...)` to handle:
  - ranged incremental edits
  - full-document fallback edits from less capable clients
  - version tracking

Validation target:

- incremental edits must produce exactly the same final document text as full replacement for equivalent edit sequences

### 4. Introduce AST caches in Java and Groovy plugins

Recommended structure:

- per-file cache entry with:
  - source hash
  - package/import summary
  - top-level declaration signature summary
  - parsed AST/root node
  - exported symbol/dependency summary

Java plugin work:

- separate top-level declaration analysis from method-body analysis where practical
- detect body-only edits versus structural edits
- reuse prior top-level symbol/dependency data on body-only changes when safe

Groovy plugin work:

- reuse module/class structure when only method/script bodies change
- keep dynamic fallback behavior conservative; if structure certainty is low, reparse fully

### 5. Persist classpath cache under `.jvmpls/`

Required work:

- define a cache directory layout, for example:
  - `.jvmpls/classpath/scan-index.json`
  - `.jvmpls/classpath/types/*.json` or a compact binary form
- persist `ClassGraph`-derived type inventory and `BinaryTypeReader` details
- validate cache entries against JAR path plus modification time
- load cache eagerly on startup and refresh stale entries in the background

Recommended boundaries:

- keep persistence logic inside `jvmpls-classpath`
- keep cache format private to that module

### 6. Persist symbol-index snapshots for warm restart

Required work:

- add a serializable snapshot model for the symbol index, references, hierarchy edges, and dependency metadata needed for warm start
- write snapshots periodically and/or on orderly shutdown
- load snapshots during startup before full background reconciliation
- reconcile with open documents and watched-file changes after load

Important constraint:

- snapshots should accelerate startup only; they must never prevent later correction by fresh indexing

### 7. Broaden executor-based concurrency

Required work:

- audit indexing and classpath operations to ensure they run through the existing virtual-thread executor
- parallelize independent file reindex jobs during workspace refresh or dependency propagation
- keep mutation points in `SymbolIndex`, `DependencyGraph`, and document state thread-safe
- avoid overlapping reindex of the same URI by introducing per-file coalescing or single-flight behavior

Recommended sequencing:

- first make scheduling explicit
- then parallelize only the work that is already deterministic and isolated

### 8. Honor `$/cancelRequest`

Required work:

- add server support for tracking canceled request ids
- thread cancellation tokens into expensive request flows:
  - workspace symbol search
  - references
  - implementations
  - call hierarchy
  - classpath-heavy definition/type-definition paths
- extend plugin execution so long-running parse/index work can check cancellation cooperatively:
  - either add an optional cancellation token parameter to `JvmLangPlugin.index(...)`, or
  - expose cancellation through `PluginEnvironment` so plugins can poll it during parse/index steps
- require Java and Groovy plugin indexing to check cancellation at stable boundaries such as:
  - before parse starts
  - after AST creation
  - before publishing symbols, dependencies, references, or diagnostics
- check cancellation between expensive phases rather than on every small operation

Minimum acceptable behavior:

- canceled requests stop producing additional work and complete quickly with an empty or canceled response path consistent with LSP4J expectations

### 9. Add benchmarks and performance tests

Phase 8 should include a reproducible performance slice rather than relying on ad hoc timing.

Recommended coverage:

- synthetic projects of roughly 100, 1000, and 10000 files using a stable baseline shape:
  - average 50 to 75 lines per file
  - typical file contains 1 top-level type with 3 to 5 methods and 2 to 4 fields
  - roughly 20% of files should implement or extend another workspace type
  - roughly 10% of files should contain cross-language Java/Groovy references
  - include a smaller script-oriented Groovy slice so benchmarks are not type-only
- metrics for:
  - cold start indexing time
  - warm start time from cache
  - single-file body-only edit propagation
  - single-file API-change propagation
  - completion latency
  - definition latency

Recommended implementation:

- place benchmarks in a dedicated module or a clearly separated test source set
- allow them to run manually or under a profile so normal CI remains stable

## Suggested Sequencing

Implement Phase 8 in this order:

1. dependency reporting hooks and `DependencyGraph` redesign
2. `ApiFingerprint` generation and direct/transitive invalidation policy in `CoreEngine`
3. incremental text sync in server and document stores
4. deterministic reindex scheduling and executor-based propagation
5. AST caches in Java and Groovy plugins
6. persistent classpath cache
7. symbol-index snapshots and warm-start load
8. request cancellation plumbing
9. benchmark/performance suite
10. final tuning, fallback hardening, and docs

This order gets the invalidation model correct before optimizing parse and startup costs on top of it.

## Risks And Mitigations

### 1. Dependency edges can be incomplete, especially in Groovy

Mitigation:

- treat dependency reporting as best-effort but conservative
- when dependency certainty is low, over-invalidate rather than under-invalidate
- keep a fallback path for explicit full workspace refresh

### 2. API fingerprinting can miss behaviorally relevant changes

Mitigation:

- scope fingerprints to exported declarations, signatures, modifiers, and supertypes
- ignore method bodies by design
- when in doubt, treat a change as API-affecting

### 3. Incremental text application can corrupt documents if range math is wrong

Mitigation:

- centralize edit application in one tested utility path
- add round-trip tests for multi-edit, multiline, and overlapping LSP change sequences

### 4. AST cache reuse can serve stale symbols or diagnostics

Mitigation:

- reuse only on body-only edits with clear structure checks
- invalidate aggressively on imports, headers, or member-list changes
- preserve a simple full-reparse fallback

### 5. Persistent caches can become a hidden source of stale startup behavior

Mitigation:

- schema-version all caches
- validate timestamps and environment inputs before load
- log cache acceptance and rejection at a debuggable level
- make cache deletion safe and automatic when validation fails

### 6. Parallel indexing can create race conditions in shared state

Mitigation:

- coalesce reindex by URI
- stage per-file results locally before publishing them into shared indexes
- add concurrency-oriented tests around repeated edits and watched-file events

### 7. Cancellation can leave partial background state behind

Mitigation:

- only publish index/cache results at stable boundaries
- use cooperative cancellation checks before commit/publish steps
- keep partial work local until it is ready to replace prior state atomically

## Validation

Phase 8 should be considered complete when:

- `textDocument/didChange` supports incremental ranges and produces correct final document state
- changing a file reindexes the file plus direct dependents, with transitive propagation only when exported API shape changes
- Java and Groovy body-only edits avoid unnecessary full structural work where caches are valid
- classpath and symbol-index warm restart paths measurably reduce startup cost on repeated runs
- indexing and cache work run on the existing executor without blocking request handling
- canceled long-running requests stop promptly and do not leave broken shared state
- benchmark runs show meaningful improvement for warm start and single-file edit propagation on synthetic projects

## Deliverable Summary

At the end of Phase 8, `jvm-pls` should feel like an incremental workspace service instead of a file-at-a-time parser: edits update only the necessary parts of the workspace, restart is faster because caches survive process boundaries, and large-project responsiveness is defended by executor-backed concurrency and cooperative cancellation.
