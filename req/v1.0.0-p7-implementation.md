# Phase 7 Implementation Plan

## Goal

Implement Phase 7 from [req/v1.0.0-roadmap.md](/home/per/project/jvm-pls/req/v1.0.0-roadmap.md): Tier 3 LSP features on top of the Phase 1-6 server, type system, classpath model, and reverse-reference index.

The target outcome is that the server moves from editor assistance into workspace-safe navigation and editing workflows:

- rename across Java and Groovy
- formatter-backed document formatting
- implementation lookup for interfaces and abstract types
- type definition navigation
- call hierarchy for incoming and outgoing method calls

Phase 7 should preserve the existing architecture:

- `jvmpls-core` owns reusable symbol, type, reference, and edit planning logic
- language plugins remain responsible for source-aware resolution and indexing
- `jvmpls-server` stays as the LSP transport adapter and workspace-settings boundary

## Scope

Phase 7 should cover:

- `textDocument/rename`
- `textDocument/prepareRename`
- `textDocument/formatting`
- `textDocument/implementation`
- `textDocument/typeDefinition`
- `callHierarchy/prepare`
- `callHierarchy/incomingCalls`
- `callHierarchy/outgoingCalls`
- core support for rename planning and validation
- core support for implementation lookup and call graph queries
- formatter delegation and workspace configuration

Phase 7 should not try to finish:

- incremental analysis and cancellation work from Phase 8
- full project-wide refactoring beyond symbol rename
- range formatting or on-type formatting unless it falls out naturally from full-document formatting support
- binary Javadoc/source attachment improvements beyond what Phase 6 already added
- framework-specific rename/call-hierarchy heuristics beyond Java and Groovy core behavior

## Assumptions

Phase 7 should build on these Phase 6 facts:

- reverse references already exist and can be extended rather than replaced
- Java and Groovy plugins already resolve symbols to shared FQNs for definition, hover, references, and signature help
- classpath and type-hierarchy data already support subtype queries well enough to expose implementations with targeted improvements
- LSP capability wiring for new request families can follow the same server pattern used in Phase 6

## Architectural Direction

Phase 7 should introduce two new reusable capabilities in core instead of implementing features as isolated LSP handlers:

1. `Edit planning`
   - rename should produce transport-neutral workspace edits in core
   - formatting should produce transport-neutral text edits even if the formatter invocation happens at the server boundary

2. `Graph queries`
   - implementation lookup should be a hierarchy query over indexed and external types
   - call hierarchy should be a callable-level graph built from reference/call-site tracking rather than reparsing on every request

The important rule for this phase is that navigation and edit features must use the same symbol identity model. If a symbol can be defined, hovered, renamed, and used in call hierarchy, all those features should converge on the same `SymbolInfo` or equivalent core key.

## Core Design Decisions

### 1. Rename needs a first-class plan model

Do not compute rename edits ad hoc inside `JvmPlsTextDocumentService`.

Recommended additions:

- `RenamePlan` model in `jvmpls-core`
- optional `RenameConflict` model for validation failures and warnings
- `CoreFacade.prepareRename(String fileUri, Position position)`
- `CoreFacade.rename(String fileUri, Position position, String newName)`

`RenamePlan` should contain:

- the target symbol
- the range/name under the cursor
- all text edits grouped by file
- validation results

This keeps cross-language rename logic testable outside the LSP layer.

### 2. Rename validation should be conservative first

Phase 7 rename should ship with predictable safety rules instead of aggressive refactoring.

Initial validation rules:

- reject renaming symbols with no stable declaration
- reject empty or syntactically invalid identifiers for the owning language
- reject conflicts where the target scope already contains a declaration with the new name
- reject constructor renames unless tied to renaming the owning type
- reject symbols whose textual rename would obviously diverge from semantic identity

Safe-first behavior is better than partial refactors that silently corrupt source.

### 3. Formatting should be provider-driven

Do not hardcode formatter binaries directly into feature handlers.

Recommended shape:

- `FormatterProvider` abstraction with a `formatDocument(...)` method
- Java and Groovy formatter providers chosen from workspace settings
- server-level process invocation or library integration behind those providers

This keeps formatting separate from semantic plugins and makes formatter choice configurable without changing LSP handlers.

### 4. Implementation lookup should be a type-hierarchy query

Do not special-case implementation search in each plugin.

Recommended additions:

- core query for `implementations(String fileUri, Position position)`
- reuse `TypeRelations` and hierarchy data for source and binary symbols
- maintain or derive a reverse subtype index for fast lookup

This should return:

- classes implementing an interface
- concrete subclasses of an abstract class
- optionally overriding methods when the cursor is on an abstract/interface method

### 5. Type definition should be distinct from definition

Do not alias `typeDefinition` to existing `definition`.

Recommended rule:

- resolve the expression or declaration under the cursor
- extract its resolved type from the Phase 4 type model
- navigate to the definition of that type symbol

Examples:

- variable usage goes to the variable declaration for `definition`, but to its class/interface for `typeDefinition`
- method call expression goes to the return type symbol for `typeDefinition`

### 6. Call hierarchy needs callable-level tracking

Phase 6 references are not enough by themselves for call hierarchy because they do not record caller ownership.

Recommended additions:

- extend reference reporting to distinguish generic symbol references from method/constructor call edges
- add a call-edge index keyed by caller callable FQN and callee callable FQN
- preserve use-site location for LSP call hierarchy items

This should support:

- outgoing calls from the selected method/constructor
- incoming calls to the selected method/constructor
- cross-language call relationships when both sides resolve to shared callable symbols

## Workstreams

### 1. Add transport-neutral edit and hierarchy models

Add or extend core models for:

- `WorkspaceEditInfo` if current `TextEdit` support is not enough for multi-file rename
- `RenamePlan`
- `RenameConflict`
- `ImplementationInfo` or reuse `Location`
- `CallHierarchyItemInfo`
- `IncomingCallInfo`
- `OutgoingCallInfo`

These should be independent of LSP4J types.

### 2. Extend core API surface

Add new `CoreFacade` and `CoreEngine` methods for:

- `prepareRename`
- `rename`
- `formatDocument` or formatter-facing edit generation hook
- `implementations`
- `typeDefinition`
- `prepareCallHierarchy`
- `incomingCalls`
- `outgoingCalls`

`CoreServer` and `ReloadableCoreFacade` should mirror these additions.

### 3. Build rename planning and validation in core

Implementation steps:

1. resolve the symbol under the cursor
2. determine the editable identifier range
3. collect all references plus declaration
4. map each use site to a file edit
5. validate local conflicts
6. return a transport-neutral workspace edit plan

Recommended initial rename support:

- classes/interfaces/enums/annotations
- methods
- fields/properties
- local variables and parameters only if plugins already expose stable declaration identity for them

Recommended defer:

- package rename
- file rename coordination
- getter/setter pair rename inference

### 4. Strengthen reference indexing for rename and call hierarchy

Phase 7 should extend indexing so references are rich enough for both rename and call hierarchy.

Required work:

- ensure declaration locations and rename ranges are stable
- track caller callable ownership for every method/constructor call
- distinguish type references, member references, and call references where needed
- keep per-file ownership so reindexing removes stale edges

Java and Groovy plugins should both emit call-edge data during normal indexing.

### 5. Add implementation search

Recommended implementation order:

1. source-only subtype lookup from indexed symbols
2. external/classpath subtype integration
3. method-level implementation lookup for overridable members

Practical core additions:

- reverse subtype map in `SymbolIndex`, or
- efficient scan plus cache over known symbols and providers

Return semantics:

- cursor on interface/abstract type -> implementing/extending types
- cursor on abstract/interface method -> overriding methods

### 6. Add type definition

Each plugin should expose a type-resolution path for expressions and declarations under the cursor.

Required behavior:

- variables/fields/parameters -> declared type
- method calls -> return type
- constructor calls -> constructed type
- collection literals or dynamic Groovy expressions -> best available resolved type, or no result when genuinely unknown

Core should convert the resolved type into a symbol lookup and location result.

### 7. Add formatter delegation

Formatting should be pluggable and configuration-driven.

Recommended first version:

- workspace settings choose formatter per language
- Java supports `google-java-format` first
- Groovy supports Spotless-backed formatting first if executable in the workspace, otherwise a configurable external command
- format full document only

Implementation pieces:

- server-side configuration model
- formatter provider selection
- process invocation with timeout/error capture
- diff current text against formatted text and return minimal or full-document `TextEdit`

Phase 7 should not depend on semantic plugins for formatting.

### 8. Add LSP wiring

`jvmpls-server` should advertise and implement:

- rename provider with prepare support
- document formatting provider
- implementation provider
- type definition provider
- call hierarchy provider

`LspTypeConverter` should map the new core models into:

- `WorkspaceEdit`
- `PrepareRenameResult`
- `Location` / `LocationLink`
- `CallHierarchyItem`
- `CallHierarchyIncomingCall`
- `CallHierarchyOutgoingCall`

### 9. Add configuration surface for formatting

Recommended workspace settings keys:

- `jvmpls.format.java.provider`
- `jvmpls.format.java.command`
- `jvmpls.format.groovy.provider`
- `jvmpls.format.groovy.command`
- `jvmpls.format.timeoutMs`

Reasonable defaults should allow the feature to be disabled gracefully when no formatter is configured or available.

### 10. Add tests by feature slice

Targeted test coverage should include:

- cross-language rename of a Java type referenced from Groovy
- rename conflict rejection inside a local scope
- rename request on unsupported symbol kinds
- implementation lookup for source and external interface types
- type definition for variable, field, method return, and constructor expressions
- call hierarchy incoming/outgoing across Java and Groovy
- formatting happy path and formatter-unavailable fallback
- LSP capability and request tests for each new feature

## Suggested Sequencing

Implement Phase 7 in this order:

1. core models and facade methods
2. rename planning and `prepareRename`
3. richer reference/call-edge indexing in Java and Groovy plugins
4. `textDocument/rename`
5. implementation lookup
6. type definition
7. call hierarchy
8. formatting configuration and provider integration
9. final LSP wiring, tests, and polish

This sequencing keeps the highest-value navigation/edit features early and postpones external tool integration until the semantic features are stable.

## Risks And Mitigations

### 1. Rename can over-edit text when symbol identity is weak

Mitigation:

- require semantic symbol resolution for all rename edits
- reject cases where only textual heuristics are available
- start with declarations and references that already share stable FQNs

### 2. Local-scope rename may not have stable identities yet

Mitigation:

- support type/member rename first
- add locals only if both plugins can expose declaration identity and reverse references safely

### 3. Formatter invocation can be environment-sensitive

Mitigation:

- make formatter execution explicitly configurable
- return no edits plus a clear error when the formatter is unavailable
- keep formatter providers isolated from semantic logic and unit-test them with fake executors where possible

### 4. Call hierarchy can become noisy if all references are treated as calls

Mitigation:

- record call edges separately from generic references
- only expose callable-to-callable relationships in call hierarchy responses

### 5. Implementation search may miss external subtypes

Mitigation:

- ship source-first if needed
- integrate classpath subtype lookup as a follow-up within the same phase before calling the feature complete

## Validation

Phase 7 should be considered complete when:

- rename works across Java and Groovy for shared symbols and rejects unsafe renames
- formatting returns correct edits through configured external formatters
- implementation and type-definition navigation work for both source and external symbols where data exists
- call hierarchy returns stable incoming and outgoing call relationships for Java and Groovy methods
- new LSP capabilities are advertised and covered by server tests
- targeted module tests pass and at least one integration scenario exercises cross-language rename and navigation

## Deliverable Summary

At the end of Phase 7, `jvm-pls` should support the full roadmap feature set for all three LSP tiers, with formatting delegated to real external formatters and with rename/navigation features implemented on the same shared symbol and type foundations built in Phases 1-6.
