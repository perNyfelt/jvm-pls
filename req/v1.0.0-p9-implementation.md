# Phase 9 Implementation Plan

## Goal

Implement Phase 9 from [req/v1.0.0-roadmap.md](/home/per/project/jvm-pls/req/v1.0.0-roadmap.md): packaging and distribution for the first `jvm-pls` release.

The target outcome is that `jvm-pls` stops being just a development workspace and becomes a releaseable product with:

- stable published Maven artifacts for embedding
- a single-file standalone server artifact for end users
- a documented, tested CLI entry point
- a repeatable release process with explicit verification gates

Phase 9 should package what earlier phases already built. It should not redesign server behavior, language features, or indexing architecture.

## Scope

Phase 9 should cover:

- finalizing the release-facing module/artifact story
- standardizing the server JAR outputs and their names
- verifying and hardening the `Main` CLI contract
- Maven Central publication metadata and release plugins/configuration
- release documentation in `README.md` and `release.md`
- a concrete release checklist that includes unit, integration, and benchmark verification
- GitHub release packaging for the standalone JAR

Phase 9 should not try to finish:

- new LSP features or semantic behavior changes
- major build refactors unrelated to packaging/publishing
- editor-specific extension packaging
- automated benchmark infrastructure beyond what is needed for release gating
- replacing the current module topology unless there is a real release blocker

- the roadmap's packaging wording is partially stale relative to the current implementation

## Architectural Direction

Phase 9 should standardize three release-facing contracts:

1. `Artifact contract`
   - every published artifact should have a clear purpose
   - the server module should expose both embeddable and standalone outputs without ambiguity
   - artifact naming should be stable across CI, docs, and GitHub releases

2. `CLI contract`
   - the standalone JAR should have deterministic startup and exit behavior
   - help/version output should be tested and documented
   - unsupported flags should fail clearly and consistently

3. `Release contract`
   - one documented command path should build, verify, and publish the release
   - Maven Central publication requirements should be represented in source control
   - release docs should tell maintainers exactly what to verify and publish

The important rule for this phase is to prefer convergence over churn. Where the repository already has a working packaging choice, such as shading instead of assembly, Phase 9 should standardize and document that choice rather than reintroducing roadmap-era assumptions.

## Core Design Decisions

### 1. Keep the current shaded standalone JAR unless it proves insufficient

The roadmap still mentions `maven-assembly-plugin`, but the repository already uses `maven-shade-plugin` successfully in [jvmpls-server/pom.xml](/home/per/project/jvm-pls/jvmpls-server/pom.xml).

Recommended direction:

- treat the current shaded `standalone` classifier as the Phase 9 baseline
- update docs and plan language to match the implementation
- only revisit assembly packaging if shade introduces a concrete blocker such as broken service loading or invalid manifests

This avoids churn in the packaging layer just to satisfy stale wording.

### 2. Publish `jvmpls-server` as the release entry point

The release-facing artifact should remain the server module, because it already owns:

- the `Main` class
- LSP transport wiring
- the standalone JAR
- the transitive dependencies on core, plugins, classpath, and build integrations

Recommended artifact story:

- standard JAR: embeddable dependency for host applications
- standalone JAR: end-user launch target
- auxiliary artifacts: sources and javadocs required for Maven Central

Modules to publish:

- publish: `jvmpls-core`, `jvmpls-classpath`, `jvmpls-build`, `jvmpls-build-maven`, `jvmpls-build-gradle`, `jvmpls-java`, `jvmpls-groovy`, `jvmpls-server`
- do not publish: `jvmpls-it`, `jvmpls-bench`

Recommended Maven action:

- set `<maven.deploy.skip>true</maven.deploy.skip>` or equivalent module-local deploy skipping in `jvmpls-it` and `jvmpls-bench`

### 3. Treat `jvmpls-bench` as a release-verification module, not a shipped runtime module

The roadmap's final module structure does not list `jvmpls-bench`, but the repository does include it.

Recommended direction:

- keep `jvmpls-bench` in the repo and aggregator
- document it as a non-runtime verification/support module
- exclude it from any release-facing module diagrams that are meant to describe shipped runtime components, or explicitly label it as optional release tooling

This preserves useful benchmark coverage without confusing consumers about what they need to depend on.

### 4. Release metadata belongs in the aggregator+parent POM unless module-specific behavior is required

Maven Central publication, signing, source/javadoc attachments, and common versioning behavior should be configured centrally in [pom.xml](/home/per/project/jvm-pls/pom.xml), which already serves the dual aggregator+parent role.

Recommended parent-level release plugins:

- `maven-source-plugin`
- `maven-javadoc-plugin`
- `maven-gpg-plugin`
- `central-publishing-maven-plugin`

Recommended publication choice:

- standardize on `central-publishing-maven-plugin` rather than `nexus-staging-maven-plugin`
- do not introduce both publication paths unless Central compatibility forces it
- keep the release workflow aligned with Central's newer publishing model

Module-local configuration should be reserved for:

- the shaded standalone packaging in `jvmpls-server`
- integration-test specifics in `jvmpls-it`
- benchmark profile specifics in `jvmpls-bench`

This keeps release mechanics uniform and easier to audit.

### 5. Use a manual release versioning flow for v1.0.0

Phase 9 should make the release versioning workflow explicit instead of leaving it open-ended.

Recommended approach:

- use `versions-maven-plugin` for explicit version changes
- perform a manual release sequence: set release versions, commit, tag, publish, then bump back to the next `-SNAPSHOT`
- do not use `maven-release-plugin` for v1.0.0

Reasoning:

- the repository already uses Maven conventionally and has `versions-maven-plugin` in plugin management
- manual `versions:set` plus tag plus deploy is easier to audit and debug for a first release
- this avoids the extra statefulness and branching assumptions of `maven-release-plugin`

### 6. CLI behavior should be tested as a public interface

`Main` is no longer just an internal bootstrap helper once Phase 9 ships.

Phase 9 should treat the following as public behavior:

- `--stdio` succeeds and starts the server
- `--version` prints a single version string and exits cleanly
- `--help` prints usage text and exits cleanly
- invalid arguments print a clear error and return a non-zero exit code

If behavior is public and documented, it should have dedicated tests.

## Workstreams

### 1. Finalize the release module and artifact model

Required work:

- document the final runtime module structure in a Phase 9-friendly way
- document `jvmpls-bench` as an internal verification module and `jvmpls-it` as an internal integration-test module
- verify that the server standard JAR and standalone JAR have the intended names and classifier conventions
- ensure the standalone artifact embeds all required ServiceLoader resources
- mark `jvmpls-it` and `jvmpls-bench` as non-deployable in Maven configuration

Expected output:

- a clear artifact table in docs and release instructions
- no ambiguity between embeddable and standalone outputs

### 2. Harden the standalone packaging in `jvmpls-server`

Required work:

- review the `maven-shade-plugin` configuration for manifest, classifier, and service merging behavior
- verify that the shaded JAR starts with `java -jar`
- confirm the published filename conventions are reflected in code and docs
- add or tighten packaging tests if current coverage is too implicit
- keep `<createDependencyReducedPom>false</createDependencyReducedPom>` and document why:
  - the standalone artifact is an attached classifier
  - dependency-reduced POM generation is unnecessary here
  - enabling it would add confusing local-build side effects for little benefit
- add manifest metadata beyond `Main-Class`, including:
  - `Implementation-Title`
  - `Implementation-Version`
  - `Implementation-Vendor`
- review shaded license/notice handling for third-party dependencies
- add LICENSE/NOTICE packaging behavior if required for compliance, for example via `ApacheNoticeResourceTransformer` or an equivalent documented approach

Specific validation targets:

- Java and Groovy plugins remain discoverable in the standalone JAR
- build tool plugins remain discoverable in the standalone JAR
- the manifest points at `se.alipsa.jvmpls.server.Main`

### 3. Formalize CLI behavior and tests

Required work:

- add focused tests around [Main.java](/home/per/project/jvm-pls/jvmpls-server/src/main/java/se/alipsa/jvmpls/server/Main.java)
- verify stdout/stderr and exit-code behavior for `--help`, `--version`, and invalid flags
- ensure `--stdio` remains the default when no arguments are given
- verify that help text and docs use the real standalone artifact name

Recommended implementation note:

- keep the CLI small and stable; Phase 9 should not expand into a large command surface

### 4. Add Maven Central publication metadata

Required work:

- add common project metadata expected by Central:
  - project name
  - description
  - URL
  - license
  - SCM
  - developers
- add source and javadoc attachments with `maven-source-plugin` and `maven-javadoc-plugin`
- add signing with `maven-gpg-plugin`
- add deployment configuration for `central-publishing-maven-plugin`
- add `<licenses>` metadata and any required repository-level license files
- ensure non-deployable modules are skipped during publish
- document the manual `versions:set` plus tag plus publish plus next-`SNAPSHOT` workflow in `release.md`

Recommended output:

- the aggregator+parent POM owns the common publication metadata and release plugin setup
- module POMs inherit it with minimal duplication

### 5. Define the verification matrix for release candidates

Required work:

- turn the roadmap checklist into explicit commands
- distinguish mandatory release gates from optional/manual checks
- include at minimum:
  - full unit test run
  - integration test run
  - benchmark profile run
  - standalone packaging build
  - smoke test of the standalone CLI

Recommended baseline commands:

- `mvn -q -DskipTests install`
- `mvn -q test`
- `mvn -pl jvmpls-it verify`
- `mvn -pl jvmpls-bench -Pbench test`
- `mvn -pl jvmpls-server package -DskipTests`
- `mvn -Prelease verify`

If these commands are too coarse or slow, Phase 9 should still publish the canonical release command sequence rather than leaving it implicit.

### 6. Write release and usage documentation

Required work:

- populate [release.md](/home/per/project/jvm-pls/release.md) with an end-to-end release playbook
- update [README.md](/home/per/project/jvm-pls/README.md) with:
  - what `jvm-pls` ships as today
  - how to build the standalone JAR
  - how to launch it
  - what Java/Maven versions are required
  - how embedding vs standalone use differ
- update any module README files that still describe pre-release assumptions

Release documentation should include:

- prerequisite credentials and environment variables for publication
- exact Maven commands
- where to find the generated standalone JAR
- how to create the GitHub release and attach artifacts
- post-release validation steps

### 7. Add CI-friendly packaging and smoke checks where missing

Required work:

- ensure CI or local verify workflows can build the standalone JAR repeatably
- add a smoke test that exercises the packaged CLI or validates the shaded artifact contents
- make sure Spotless and SpotBugs remain part of the release-quality gate
- tighten SpotBugs for release verification:
  - either set `failOnError=true` unconditionally
  - or add a `release` profile that flips SpotBugs to fail the build on findings

This work should improve confidence that a release candidate is actually publishable, not just compilable.

## Suggested Implementation Order

1. Normalize the Phase 9 target around the current shaded packaging model.
2. Add aggregator+parent publication metadata and release plugins.
3. Harden the server packaging and add CLI/packaging tests.
4. Document the release commands and artifact story in `README.md` and `release.md`.
5. Run the full release verification matrix and fix any packaging regressions.
6. Perform one dry-run release from a clean workspace before attempting a real publication.

## Deliverables

Phase 9 should be considered complete when the repository contains:

- a finalized `jvmpls-server` packaging configuration for standard and standalone JARs
- tested CLI behavior for `--stdio`, `--version`, and `--help`
- Maven Central-ready metadata and publication configuration
- explicit non-deployable configuration for `jvmpls-it` and `jvmpls-bench`
- a non-empty [release.md](/home/per/project/jvm-pls/release.md) with an explicit release procedure
- updated top-level docs that explain how to build and run the standalone server
- a release checklist tied to concrete commands and pass/fail criteria

## Acceptance Criteria

- `mvn -pl jvmpls-server package -DskipTests` produces the standard JAR and the standalone classifier JAR.
- `java -jar ...-standalone.jar --help` prints valid usage text.
- `java -jar ...-standalone.jar --version` prints the expected version.
- service-loaded language and build plugins are present in the standalone artifact.
- the aggregator+parent POM metadata is sufficient for Maven Central publication.
- `jvmpls-it` and `jvmpls-bench` are excluded from deployment.
- release verification uses a SpotBugs configuration that fails on findings.
- `release.md` tells a maintainer exactly how to cut a release without relying on tribal knowledge.
- the release checklist includes unit tests, integration tests, and benchmark validation.

## Risks and Mitigations

### 1. Packaging drift between docs and build

Risk:

- the roadmap, README, and actual Maven packaging can describe different artifact names or plugins

Mitigation:

- standardize on the current implementation and update the docs in the same change set

### 2. Shaded JAR can silently break ServiceLoader behavior

Risk:

- the standalone JAR may build successfully but fail to discover plugins at runtime

Mitigation:

- add explicit smoke checks for language/build plugin discovery in the packaged artifact

### 3. Maven Central publication can fail late due to missing metadata

Risk:

- the build looks healthy locally but deployment fails on missing SCM/license/signing/source/javadoc requirements

Mitigation:

- add publication metadata early and dry-run the release path before tagging

### 4. Benchmark gating can become aspirational instead of enforceable

Risk:

- the roadmap requires acceptable benchmark thresholds, but the repo only has benchmark code, not release thresholds

Mitigation:

- Phase 9 should at minimum define the benchmark command and the reporting expectation
- if hard numeric thresholds are not ready, document that as a follow-up rather than pretending the gate exists

## Open Questions

- Do we want a dry-run GitHub release workflow in CI, or is the release process intentionally manual for v1.0.0?
- Are benchmark thresholds ready to be codified, or should Phase 9 define the measurement process and defer hard limits?
